## A B C 会话职责

| 类型 | 允许工作 | 边界 |
|---|---|---|
| A 新页面或业务增量 | 按批准任务卡实现一个页面/基础包，可包含多个未冻结模块的必要增量，代码各归所属模块 | 不修改已验收旧行为或冻结范围；旧缺陷交B，不顺手修复；未授权依赖不越界 |
| B Bug 修复或重构 | 基于旧模块源码、模块文档和具体问题，完成单一修复或明确重构 | 不开发全新业务模块；重构范围和缺陷范围分别说明，不夹带扩展需求 |
| C 设计与文档审查 | 只读代码，设计下一页面及必要模块能力或按授权修订文档、接口草案、表及验收场景 | 不写业务实现；已批准契约变更需评审，未批准草案可在授权范围内修订 |

每个会话明确页面子范围、涉及模块、基线提交、分支、工作目录、允许修改路径和禁止修改路径；以 `.prompt.md` 模板交接。缺陷记录和待决事项可以交付为文档，不自动触发另一个会话或授权发消息。

## 文件与 Git 隔离

并行编码必须使用独立 worktree 或独立克隆目录。两个独立对话使用同一目录，仍可能互相覆盖；同一目录反复切分支也不能解决同时修改问题。

本环境新建分支使用 `codex/` 前缀，例如 `codex/feature-m04-ingest`、`codex/fix-m04-issue`、`codex/design-m04`。保留已有 `docs/project-definition`，不为命名统一改动现有分支，不自动创建所有分支。

各会话从明确、已集成的提交开始。一个人承担集成职责，逐个评审和合入；后续模块在包含已批准修复的基线上继续，不盲目覆盖旧版本。共享路由入口、依赖清单、公共契约或全局文档有冲突时，由集成人协调修改顺序。

仓库权限、保护分支和 CI 路径检查应由技术负责人落实。提示词只能约束协作行为，不能代替访问权限和自动检查；本批文档没有配置 GitHub 保护规则或 CI。

## 冻结的含义

“冻结”保护一份已验收基线，不等于永远不能修复。开发完成、测试完成、合并、部署、业务验收分别登记。

页面子范围可以先验收冻结；当前可测状态登记在第12份。页面独立API通过不自动关闭跨页联合回归或HW验收。模块剩余功能仍未交付时不能冻结整个模块。冻结范围记录行为、路径与契约，不只记录目录名。

模块或明确子范围冻结需要：

1. 源码和模块文档已保存并纳入版本控制；公开接口与表归属一致。
2. 验收场景执行完成，记录输入、预期、实际、环境和证据位置；区分模拟与真机。
3. 记录验收人、基线提交、模块版本、修改路径和已知限制。
4. 项目负责人或其明确指定的验收人批准后，将模块状态改为已验收冻结。

后续 B 会话对冻结模块的修复形成新分支和新版本；复验后更新冻结基线，保留旧版本追溯。A会话需要扩展已冻结接口时，先由C形成兼容方案及独立变更工作包，批准并完成后再使用；同模块未冻结能力可在授权页面工作包内新增。B会话不夹带全新业务。

共享文件可以在任务中明确列入允许修改清单，例如新模块的路由注册与依赖注入入口；这不授权修改旧模块业务行为。禁止修改路径优先，发现交叉必须先澄清范围。

## 代码与数据硬边界

- 不跨模块写数据库、不直接调用其他模块内部服务，不把全业务堆入一个类或共享工具目录。
- 不回退、清理或覆盖无关用户改动，不删除原始资料，不在原 V1.0 文件中静默改范围。
- 不将本批设计草案标为已批准，不将示例数值、样例图和模拟数据标为真实检测。
- 无效、未检测、缺测不判合格；报警确认不覆盖原始超限；旧配方记录不随新规则静默重算。
- 产品1/2底层算法、生产控制、机械动作及 PLC 写入不在本期默认授权内。
- 文件、日志、截图中的凭据不得写入仓库；用户提供的资料不自动获准发布到公开 GitHub。
