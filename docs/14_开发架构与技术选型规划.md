## 2 建议技术组合

### 2.1 保持现有开发语言

| 层次 | 推荐 | 原因及边界 |
|---|---|---|
| 业务前端 | 现有React＋TypeScript＋Vite＋ECharts | 直接复用页面与交互，不更换组件风格或重做路由 |
| 管理前端 | React＋TypeScript，同一设计基线 | 独立构建入口，无须微前端框架 |
| 平台后端 | Node.js＋TypeScript＋NestJS，首期使用默认HTTP适配器 | 与前端同语言，明确模块、依赖注入、入口和权限校验职责 |
| 数据访问 | pg驱动＋参数化SQL＋模块私有Repository | 接收去重、事务和统计SQL可直接审查；避免同时引入多个ORM |
| 数据迁移 | node-pg-migrate稳定版候选，受控SQL或TypeScript迁移 | 与Node工程一起管理；禁止生产自动同步表结构 |
| 主数据库 | PostgreSQL，优先评估既有候选17系列的受支持补丁 | 复用已有逻辑设计；具体补丁与镜像摘要在G00验证锁定 |
| 设备本地存储 | SQLite，只有需要离线持久化的采集端启用 | 单机队列、快照和补传；不另建数据库服务器 |
| 模拟器 | 独立TypeScript＋Node.js程序 | 与平台仅通过公开契约协作，可CLI起步，后续加控制页面 |
| HTTP入口 | 现有Nginx | 同源静态文件、API反向代理、生产TLS入口 |

Nest支持TypeScript及模块公开导出，适合映射已有M00—M10边界，但框架本身不会自动禁止跨模块读表；仍需导入规则和评审。[Nest入门](https://docs.nestjs.com/first-steps)、[模块机制](https://docs.nestjs.com/modules)。本项目选Nest是维护边界的判断，不是已经证明其性能优于其他框架。

pg事务中的语句必须使用同一连接；连接池与事务上下文应封装在基础设施中，业务模块不能混用不同连接完成同一事务。[pg事务说明](https://node-postgres.com/features/transactions)。迁移工具支持JavaScript、TypeScript及SQL；实施时选兼容的稳定版本，不直接照用文档站展示的alpha版本。[node-pg-migrate](https://salsita.github.io/node-pg-migrate/)。

### 2.2 版本和语言例外

前端以当前package-lock.json为基线，不借后端选型整体升级。现有Docker构建使用Node 22；后端候选必须核对Node、TypeScript和Nest的实际兼容范围，再锁定补丁、依赖与镜像摘要。语言不变不等于永远不能维护运行时安全补丁；升级另立变更。

平台保持Node/TypeScript；设备端按供应方SDK、系统、采样频率、同步和离线需求验证技术选择。开放协议且性能适用时可用TypeScript；专用SDK可选其原生支持语言并记录依据，不强行桥接以牺牲采样可靠性。设备端语言变化不改变平台统一契约。

### 3.3 后端内部组织

沿用已经预留的 `apps/platform/modules/mXX-*/`，后续每模块按需增加：

```text
api/              对其他模块公开的接口、DTO与事件
application/      用例、权限检查、事务编排
domain/           状态与规则，不依赖HTTP或数据库
infrastructure/   本模块SQL、文件或外部系统适配
presentation/     HTTP入口、输入校验与响应映射
```

平台启动文件和模块装配放composition，配置放config，迁移统一放db/migrations并在文件名标所属模块。不同时建立Java目录和TypeScript目录。简单只读查询允许直接返回DTO，不机械创建大量空转发类。跨模块只允许导入api公开项，禁止deep import仓储或直接使用其他模块表；后续静态检查验证这一点。

### 3.4 首期不拆微服务

当前主要难点是规则、记录真实性、断网恢复和业务闭环，没有已确认的独立团队、吞吐或发布频率要求支持全面微服务化。首期拆11个服务会增加网络故障、鉴权、分布式事务、监控和部署成本。

已经确定独立运行现场采集与分析worker；它们不等于拆分11个微服务。后续出现明确瓶颈，再评估业务服务拆分：M07客户集成、M06报告渲染、M04高吞吐接收分别可能成为候选，但必须先给压测与故障影响证据。拆出后唯一数据所有者、兼容API、迁移回退和运维责任必须明确；不预先上注册中心、配置中心或服务网格。

## 4 数据库和文件存储

### 4.1 一个业务库，按模块归属组织

PostgreSQL保存平台业务数据。建议一套实例、一个业务库，使用m00至m07的schema区分所有者；M08集中配置若同库则另归m08。schema是命名和权限组织方式，不是8个数据库或8个服务，亦不会自动阻止同一数据库账号越界。

普通运行账号不拥有DDL权限，迁移账号单独使用；模块边界由Repository、导入检查和SQL审查保证。需要更强隔离时再使用模块独立数据库角色及受控连接策略，不能在没有配置前声称已有数据库级模块隔离。factory_id及实际资源范围由服务端校验。

| M01 | factory、production_line、inspection_process、device、product_specification |

### 4.2 类型和测量精度

ID用uuid候选；时间用timestamptz并保存来源时间与接收时间；测量值用numeric，API用十进制字符串。TypeScript服务端引入经验证的十进制运算库或明确的整数缩放方法，不能把字符串转换成普通Number后直接作临界值判定。单位、精度、舍入和比较规则需黄金样本验证。numeric可存精确十进制，不代表原仪器没有测量误差。[PostgreSQL数值类型](https://www.postgresql.org/docs/current/datatype-numeric.html)。

jsonb只保存带版本的协议原文、快照和扩展辅助量；设备、任务、时间、稳定记录键等检索字段使用独立列。原始记录不覆盖；更正追加修订，历史报告冻结。演示数据不批量迁入生产；合法初始化档案另用有来源的导入流程。

### 4.3 索引、容量与分区

先实施第04份的唯一约束和按工厂、任务、设备及时间查询的复合索引。接收使用稳定来源键去重；分页固定接收截止点与稳定排序；曲线限制点数，保留异常定位，原始记录不因画图降采样被删除。

日记录数约为设备数×每秒入库记录数×每日有效秒数。仅作容量演算：3台×10条/秒×86400秒=259.2万条/日；若每条实际占用按1KB估算，则原始量约2.59GB/日，未含索引、WAL、事件、附件及备份。这不是设备能力或配置承诺，须用真实报文测量实际占用。

先取得峰值/平均频率、批次大小、保留期和图像量，再决定是否分区或归档。分区前重新设计跨分区唯一性，不能把sample_time随意加入唯一键而破坏全局去重；必要时用独立去重登记。只有普通索引、批量写入与保留策略仍无法达标，才评估时序扩展或独立分析存储。

### 4.4 附件与日志分开

图像、PDF和导入原文件首期放受控持久目录；数据库保存所属范围、storage_key、摘要、大小、状态与保留策略。下载走鉴权，文件不放前端public目录。上传先暂存并校验，再登记可用状态；中途失败有清理和对账，数据库成功不代表文件必然存在。

审计日志是M00追加业务数据，保存在PostgreSQL。运行日志采用脱敏JSON及轮转文件/标准输出，不把全部调试日志写进业务库。后续后台查询通过受限日志读取适配器限定服务、时间和数量，不接受任意文件路径或shell命令，不给平台挂Docker socket。首期可先只提供业务审计及有限运行诊断，跨主机全文检索需要时再引入日志平台。

### 4.5 SQLite只用于本地端

M09需要离线检测时，本地保存任务快照、原始数据、上传队列及逐条回执；SQLite位于设备主机本地磁盘，不能让多台设备共享网络盘上的同一数据库文件。建议单写入队列，WAL/同步级别和断电行为实测锁定；备份采用一致性备份方式，不仅复制活跃主文件。[SQLite适用场景](https://sqlite.org/whentouse.html)、[WAL约束](https://sqlite.org/wal.html)。

仅内存生成样本的轻量模拟器不必用SQLite；测试进程重启、断网积压和持久补传时，再使用本地持久队列。平台不能跨网络查询设备SQLite表。

## 5 为数据模拟器预留稳定接入边界

### 5.1 模拟器的位置和职责

规划路径为 `tools/simulator/`，本次不创建实现。它独立启动、独立配置、独立保存场景和运行记录，不能导入platform内部服务或直接写数据库，也不通过浏览器localStorage注入数据。平台不增加仅用于测试的“生成下一条”“重置生产数据”接口。

建议结构：scenarios存场景，generators生成样本，transport实现上传及故障注入，state保存运行与补传状态，cli为首期入口。后续模拟器控制页面只控制模拟器自己的进程；不放进正式管理后台，不随生产包默认启动。

两种模拟目标分开登记：

1. 平台契约模拟：直接发送规范上传包，验证真实API、数据库、报警、查询和报告链路。
2. 厂商协议模拟：未来按真实协议发原始字节或厂商报文，经过真实适配器再上传，验证驱动解析与协议边界。

第一类不能证明串口、SDK、相机算法、测量精度或第二类协议兼容，更不能替代HW真机验收。

### 5.2 模拟器和真机共用的契约

以第05份为语义基线，先在 `contracts/devices/`、`contracts/openapi/` 完成可校验Schema与样例，再独立开发模拟器和M04。契约中snake_case字段及三项稳定指标码不由前端dg/jx/by直接替代。

| 能力 | 规划接口或契约 | 实施前必须固定 |
|---|---|---|
| 身份 | M00设备凭据，独立于人员登录 | 设备与工厂范围、REAL/SIMULATED许可、撤销和到期 |
| 测量上传 | POST /api/v1/measurements:ingest | schema_version、逐条记录、大小/批量上限、错误及回执 |
| 心跳 | POST /api/v1/device-status:heartbeat | 设备会话、任务/配置观察版本；心跳不等于有效采样 |
| 源报警 | POST /api/v1/source-alarms:ingest | 触发/恢复事件ID、生命周期键、顺序与回执 |
| 证据 | POST /api/v1/evidence及受控引用 | 文件限制、来源范围、摘要、失败状态；无图像可为空 |
| 任务规则 | M02/M03面向接入端的只读快照契约 | 获授权任务、冻结版本、实际切换确认；路径在专项设计定稿 |

这些路径是既有草案，不是当前可调用服务。正式接收契约至少固定：record_id、device_id、task_id、source_session_id/source_sequence（按能力可空）、sample_time、time_source、位置与质量、recipe_version_id、指标值/单位/有效性、raw版本和evidence_refs。缺少序号不能伪造新样本身份，读取快照需明确sample_kind。

回执STORED、DUPLICATE、QUARANTINED、REJECTED分别处理；HTTP 200不等于所有记录成功。只有平台可靠持久化后才确认接收。重试保留原record_id、样本内容和采样时间；同键异内容应冲突。拒收和隔离记录保留可诊断状态，不能无限重试或静默丢弃。

### 5.3 模拟和真实来源的隔离

首选单独Compose测试项目、数据库、附件目录及凭据。即使共用部署也必须由服务端凭据绑定data_environment并贯穿记录、报警、统计、报告及事件，不能信任上传方自行填写REAL。模拟器将字段改成REAL应被拒绝，而非产生正式实测记录。

初始工厂、设备、盘号、批准测试配方和任务由授权测试准备脚本调用正常管理API建立，或由受控测试夹具建立；模拟器不能临时编造不存在的task_id并让平台自动放行。设备凭据仅有上传和必要快照读取权限，不获得账号管理权限。

模拟器只配置测试目标白名单，默认不开生产目标；MES使用独立假接收端或禁用出站，避免压测数据被送到客户系统。测试标识是业务来源元数据，不是特殊成功分支；相同API、校验和持久化流程均要执行。

### 5.4 可复现的场景合同

每次运行保存run_id、场景版本、随机种子、契约版本、设备集合、任务映射、计划样本清单及实际逐条回执。同一运行断点续传保留原键；另开一次运行使用新命名空间，避免重放场景与新实验混淆。场景预期结果保存独立黄金样本，不能调用平台同一判定函数来生成“正确答案”。

| 场景 | 平台必须表现出的结果 |
|---|---|
| 正常、边界、超限 | 按已批准测试规则完整精度判定；曲线、历史和报警可定位同一记录 |
| null、无效、缺方法 | 不把空值当0，不判合格；有合法原值则保留 |
| 原键重发、原键篡改 | 前者返回DUPLICATE不多存；后者冲突且不覆盖 |
| 多台同类设备、多任务及切盘 | 数据只进入已核实任务；切换未确认不猜新盘号 |
| 乱序、迟到、时钟漂移、序号重启 | 来源和接收时间分别保存，按已定契约处理，不按接收顺序伪造过程 |
| 已写库但回包丢失、断网、进程重启 | 原键补传；持久队列可恢复，核对缺失、重复和隔离集合 |
| 心跳正常但数据停更 | 在线状态与陈旧状态分开显示 |
| 平台返回429/503、凭据撤销 | 有限退避及积压可见；权限失败停止盲目重试 |
| 源报警恢复先到、事件重复 | 生命周期不错误回退；消费去重和顺序策略可核对 |
| 峰值与持续负载 | 记录实际吞吐、延迟、积压与资源；按事先批准目标判断 |

### 5.5 如何减少以后改动

JSON/OpenAPI Schema是跨进程契约源，TypeScript客户端类型由其生成；类型检查不能代替运行时校验。版本、错误码、单位、空值、稳定键及回执先定；设备专有字段只留在适配器和版本化raw中。新设备通过能力映射接入，不在每个页面增加按厂商分支。

契约测试至少覆盖一版旧客户端、当前客户端及不支持版本。增加字段有兼容策略；改单位、含义、必填项或回执语义需新版本和迁移。模拟器替换为真实适配器时，平台只更换注册设备、凭据、配置及必要能力映射；如真实协议揭示新业务事实，仍需受控变更，不能承诺永远零改动。

## 6 不使用消息中间件时怎样保证可靠性

### 6.1 同库事务和持久事件

记录及M04自己的measurement_outbox同事务提交，然后才返回接收结果。后台调度调用发布模块公开的claim/ack/retry能力；它不直接写各模块事件表。消费者在自己的事务内写业务结果和consumer_receipt，失败不留成功收据。

首期同进程可以同步调用已注册消费者的公开事件入口，但从持久outbox恢复，而非只用内存EventEmitter。一个事件发给多个消费者时，采用发布方所有的逐消费者投递状态，或在全部已启用消费者成功后才完成总事件；不能第一个消费者成功就把事件标完。新增投递状态属于第04份待细化迁移增量。

调度租约过期可恢复，处理后确认前宕机允许重发，消费者幂等保证业务不重复。短事务认领后再处理，网络请求不长时间占用数据库事务。PostgreSQL的SKIP LOCKED可用于队列竞争，但不应拿它跳过普通业务查询需要看到的数据。[SELECT锁定说明](https://www.postgresql.org/docs/current/sql-select.html)。

### 6.2 审计和报告完整性

关键业务写入与待审计事实同事务保存，再由M00的受控追加能力落审计；M00自身操作可同模块事务直接审计。异步审计应有积压监控、重放和幂等；审计页标明查询截止，不把尚未同步的窗口展示成完整无记录。若某操作要求审计立即可见，专项设计明确通过M00公开接口参与受控事务，不能直接写M00表。

报告生成固定输入清单、规则和资格版本、接收截止及处置消费水位。测量入库而报警尚未处理时返回未就绪，不能输出看似完整的最终报告。文件生成失败与业务任务状态分别保存，重试不覆盖已发布文件。

### 6.3 MES和现场故障

M07自己的投递表记录不可变业务载荷和每次尝试。仅收到客户业务确认才ACKED；HTTP成功、部分接收、响应丢失各自处理。客户没有幂等或回执查询能力时明确人工对账方案，不宣称端到端恰好一次。

平台故障时M09继续已具备有效任务和规则条件的本地采集；缺任务或规则不能沿用上一盘。磁盘满、仪表离线、缓存到限必须显式报警并按批准策略停止可靠记录/判定，不静默丢弃后仍显示正常。浪潮离线补传能力由供应方协议确认，不由平台架构推定。

## 7 管理后台与现有页面怎样继续开发

### 7.1 两个Web入口共用一套平台

业务前端继续使用现有路由和页面。管理后台未来放apps/admin-web，建议部署在同域/admin/路径，仍访问同一套/api/v1。账号、会话、角色和工厂权限由M00统一处理；不另建admin_user库，不要求浏览器直连数据库。

现有P25用户、P26审计、P27设置先接真实API，保留所有入口。AD01账号角色、AD02审计、AD03运行日志、AD04平台设置按第13份后续实现；若迁移现有入口，先安排兼容跳转和权限验证，不同时复制两套独立业务逻辑。后台样式复用当前设计，按真实共用部分提取纯展示组件。

### 7.2 最小身份方案

建议服务端Cookie会话，HttpOnly、生产Secure及明确SameSite，写请求校验CSRF；会话放PostgreSQL，首期不为会话引入Redis。选用维护中的认证/会话组件，不自行设计密码算法。具体库、口令策略、会话期限在P01定稿。禁用用户或撤权应使后续受保护请求按契约失效；前端隐藏按钮不代替后端权限。

设备上传使用单独的可撤销凭据及设备范围，不能使用人员会话。管理后台查日志或导出仍需独立动作权限和数据范围；系统管理员不自动具有质检批准权限。

### 7.3 逐页替换数据来源

为每页定义明确的客户端接口，由demo适配实现与HTTP实现分别提供。部署模式显式选择；API失败不能回退演示数组，生产构建不得提供任意密码、故障模拟或重置入口。UI/错误反馈按现有风格扩展，不更换配色和布局。

保留原型的交互基线，核对每个字段映射；例如dg/jx/by、pending/running/completed只在边界转换，不直接写成生产契约。首轮采用有上限的轮询，展示频率与采样/上传频率独立；真实负载需要时再选SSE或WebSocket，不先增加消息代理。

## 8 部署和中间件取舍

### 8.1 首期最小部署

目标是同一Docker Compose项目内三个常驻容器：web/Nginx、platform、postgres；一次性迁移任务不算常驻服务。管理Web完成后其静态文件由同一Nginx提供。SQLite是设备进程的本地库，不是第四个数据库容器。模拟器单独的测试profile或测试项目，生产默认不启用。

保持当前本机4181入口，后端与数据库仅内部网络访问；需要开发调试端口时仅绑定回环地址。生产HTTPS及客户网络策略另定。platform使用独立持久附件卷；postgres使用数据库卷；日志有轮转及容量限制。健康检查区分进程存活和数据库等依赖就绪，不因MES离线把整个采集链强制判死。

当前Compose仍只有web，本方案没有提前添加不可运行的服务。后续先写完整配置、版本、环境变量和镜像清单，再由用户获取所需镜像。

### 8.2 引入条件

| 组件 | 首期结论 | 当前替代办法 | 何时才值得引入 |
|---|---|---|---|
| PostgreSQL | 必需 | 不用localStorage存正式业务 | G00建立真实后端时 |
| Nginx | 保留 | 已有静态入口，后续代理API | 现在已有；代理增量另验 |
| SQLite | 条件必需 | 不需离线的程序不安装 | 设备端持久补传或模拟器重启恢复测试 |
| Redis | 不引入 | PostgreSQL会话、索引、受控查询 | 实测证明共享缓存/限流瓶颈，且有失效及降级方案 |
| RabbitMQ/Kafka等 | 不引入 | 所属模块outbox、消费收据及数据库调度 | 多独立消费者跨进程、大量积压或分发需求有实证 |
| MQTT Broker | 不引入 | 规范HTTP接入 | 厂商实际协议要求MQTT；它与平台业务事件队列分开评估 |
| 对象存储 | 不引入 | 单机受控文件卷＋元数据 | 多节点共享、对象规模或客户存储规范需要 |
| Elasticsearch/OpenSearch | 不引入 | 审计SQL查询，有限范围运行日志 | 跨主机全文检索及规模超出当前方案 |
| 时序库/分析库 | 不引入 | PostgreSQL索引、批量、保留及按需分区 | 真实压测与长期成本证明需要 |
| Prometheus/Grafana等 | 暂不部署独立栈 | 健康、结构化日志、积压和容量指标 | 需要长期趋势、统一告警或多节点运维 |
| API网关/注册中心/Kubernetes | 不引入 | Nginx＋Compose＋受控配置 | 独立服务数量、可用性与运维团队支撑 |

### 8.3 备份、离线交付和容量

数据库与附件都要备份，备份存到不同故障域；不能仅备份Compose配置。初期可选择逻辑备份，恢复点要求更严格时规划基础备份和WAL归档。恢复需核对数据库中引用的文件摘要；采用一致性快照/暂停写入窗口，或明确能够对账的备份清单。[PostgreSQL备份与恢复](https://www.postgresql.org/docs/17/backup.html)。

离线交付包含镜像、依赖清单、迁移、配置模板、校验值和恢复步骤。设备数、入库频率、保留期、图像量、RPO/RTO未确认前不给固定生产硬件或“永不丢数据”承诺。单机Compose本身不提供高可用，客户若要求不停机需另作冗余设计。
