## 吞吐与容量重点

- M04 每批最多 500 条/1 MiB，逐条事务；OVALITY 在设备级事务锁内逐点调用 InfluxDB HTTP，超时 8 秒。实际吞吐上限尚未压测。
- 凭据级限流 120 次/分钟，IP 600 次/分钟；共享凭据、心跳、绑定查询和重试共用预算。Nginx 后面的客户端可能聚合为同一 req.ip；需要核实代理信任配置。
- InfluxDB 每点独立 `point` tag、原文 base64 存储、读取每组 50 点且全时间范围。需要批量写入、有限时间查询和标签基数实测；不以单点 ID tag 的便利替代规模验证。
- PostgreSQL 每点仍保留事实索引、值元数据、判定、资格、投影、outbox 等多表记录；不是“采样进时序后 PG 不增长”。任务统计为增量触发器，热点任务持续更新同一行。
- 趋势首次按每页 100 条下载完整原文。当前实测 25 条明细约 181 KiB；应增加轻量数值趋势 API、按时间窗口分辨率返回首末/极值并支持原始点钻取，保留完整时间跨度。
- 50 Hz × 86,400 秒 = 432 万点/设备·天；10 台 = 4,320 万点/天。此为计算示例，不是设备承诺频率或已达到吞吐。保留周期、索引、WAL、备份容量须按实测字节/点另算。
- analysis-worker 当前仅写 health-only 心跳；M05/M06/M07 虽有服务代码，不能把进程健康当作报警、分析或 MES 持续消费已运行。
- PG 和 InfluxDB 无跨库事务：时序成功而 PG 失败会留下不可见孤立点。来源键重试基础已具备，仍需对账、孤立点巡检及联合恢复演练。
